# design-game

Пайплайн гейм-дизайна по линзам Джесси Шелла на любом масштабе — от игры на пять минут до большого проекта. Колода: 113 линз книги своими словами, линза 93½ из третьего издания и две наши с пометкой «не Шелл».

**Режим по умолчанию — `co-design`**: в гейм-дизайне ставки делает человек, агент спорит, записывает, зондирует и сверяет. Гейт — после каждой стадии. Остановка в любом режиме — на всём, что уходит наружу от имени владельца.

## Где что лежит

Все пути — от папки этого файла: в Claude Code это `${CLAUDE_SKILL_DIR}`, в Codex — папка, откуда прочитан этот файл (`~/.agents/skills/design-game/` или `<проект>/.agents/skills/design-game/`). Скрипты запускаются так: `python -X utf8 <папка скилла>/scripts/<скрипт>.py …`; если команды `python` нет — `python3`.

| Что | Где |
|---|---|
| Что делать в ситуации | `WIKI.md` |
| Шаги стадии N | `stages/NN-*.md` — читать только текущую стадию |
| Линзы | `lenses/lenses.json`; набор стадии — только через `scripts/pick_lenses.py` |
| Когда какая линза | `stages/stages.json` |
| Правила метода | `method/`: цикл и гейты, канал владельца, статус знания, слои по паспорту, папка игры, зонды |
| Шаблоны | `templates/`, шаблоны файлов стадий — `templates/stages/` |
| Роли | агенты `gd-*`: в Claude Code с плагином — `design-game:gd-…`, без плагина — `gd-…`; в Codex роль зовут по имени `gd-…` в запросе |

## Принципы

1. **Управляющая идея — стержень.** Формулируется на стадии 0, стоит в шапке каждого файла стадии; элемент, который её не усиливает, — кандидат на вырезание. На `mini` она короче, но есть всегда.
2. **Опыт держит человек.** Агент игру не переживает: его суждения об опыте и аудитории — гипотезы до наблюдений людей, у них стоит статус знания (`method/knowledge.md`).
3. **Правило цикла.** Игра становится лучше от числа кругов «проверили — исправили». На каждом гейте вопрос: какая проблема теперь и какой риск самый крупный — дальше или возврат на любую стадию (`method/cycle.md`).
4. **Детерминированное делают скрипты.** Подбор линз, проверка стадии, входящие владельца, карточка гейта, Библия, окупаемость. Линзы на глаз не подбираются, готовность стадии модель сама не объявляет.
5. **Один файл стадии — один писатель.** Стадии идут по порядку; параллельно — только зонды разных рисков в пределах гейта.
6. **Зонд одноразовый.** Один вопрос, самая лёгкая форма. Код зонда в сборку не переносится — правило наше, строже книги; константы и выводы переносятся.

## Шаг 0 — вход

**Папка игры уже есть** (в ней `00-heart/CONTROLLING-IDEA.md`) — это «продолжим игру»: `scripts/init_game.py <папка>` без имени и масштаба досоздаст недостающее, не тронет существующее и напечатает таблицу состояния стадий — читай её из вывода, а не всю Библию. Затем `scripts/inbox.py <папка>`. Продолжай с первой стадии не в `OK` или `SKIP`: стадия в `GATE` — покажи её карточку, в `DRAFT` — зови её роль, в `ЖДЁТ ВЛАДЕЛЬЦА` — напомни вопрос.

**Новая игра** — бриф одним сообщением по шагу 1 `stages/00-heart.md`, у каждого вопроса твоя рекомендация. Свойства и риски сначала выведи из идеи сам, потом дай подтвердить; режимы автономии объясни по `method/owner.md`. Затем `scripts/init_game.py <папка> --name "…" --scale …` и паспорт в разделе «Паспорт игры» файла `00-heart/CONTROLLING-IDEA.md`. Пока паспорт не заполнен, `pick_lenses.py` останавливается с ошибкой — так и задумано.

## Круг стадии

Для каждой стадии N по `stages/stages.json`:

1. **Входящие.** `scripts/inbox.py <папка игры>`: каждый ответ — дословно в таблицу вопросов стадии и строкой в `logs/DECISIONS.md`; под комментарием — `> [!agent]`, тег меняется на `[!owner-ok]`. Ответ, меняющий закрытую стадию, — возврат, а не тихая правка.
2. **Роль.** Мини-ТЗ роли стадии (`stages.json` → `agent`): папка игры, папка скилла, стадия, режим, прото, цель и критерии приёмки и команда `pick_lenses.py <папка игры> --stage N` — роль запускает её сама и вписывает первую строку вывода в шапку; текст линз ты не пересылаешь. Роль работает по `stages/NN-*.md` и шаблону стадии. Стадию 0 ведёшь ты сам, огранку идеи поручаешь `gd-concept`.
3. **Режим в роли.** `co-design` — роль идёт до первой развилки и возвращает вопросы `Q-NN.k` с рекомендациями; ты спрашиваешь владельца и зовёшь роль снова с ответами. `assisted` — роль делает стадию целиком, развилки идут вопросами на гейт. `auto` — роль делает стадию целиком, свои решения помечает `[!auto]`, ты переносишь их строками `auto` в `logs/DECISIONS.md`.
4. **Зонд** — если верх `logs/RISKS.md` закрывается пробой: `gd-prototyper` проектирует, `gd-builder` собирает и прогоняет (браузер через Playwright MCP или движок через его MCP). Агент-игрок `gd-player` — на любом зонде любой стадии, но только когда `scripts/check_stage.py <папка игры> --stage 0 --audience` даёт код 0; его вывод — «предположение модели». После зонда снова зови роль стадии с путём к `probe.json` и отчётам агента-игрока: вывод в файл стадии вносит она.
5. **Проверка.** Роль сдаёт стадию со статусом `DRAFT` после `scripts/check_stage.py <папка игры> --stage N --before-keeper`; пока проверка не `OK`, дальше не идём.
6. **Сверка связности.** `gd-keeper` получает команду `pick_lenses.py <папка игры> --stage N --gate`, пишет `logs/CONSISTENCY.md` и ставит вердикт. После вердикта ты ставишь в шапке файла стадии: `OK` или `DRIFT` хранителя → `GATE`; `ЖДЁТ ВЛАДЕЛЬЦА` → `ЖДЁТ ВЛАДЕЛЬЦА`; `BLOCK` → `DRAFT` и показываешь владельцу блок «Возврат» из сверки вместо карточки.
7. **Гейт.** `scripts/build_bible.py <папка игры>`, затем `scripts/gate.py <папка игры> --stage N --mode <режим>` — карточку показываешь владельцу как есть.
8. **Решение** записывает скрипт: принял, в том числе при `DRIFT` с переносом вопросов, — `gate.py … --accept`, стадия получает `OK`; возврат — `gate.py … --return M`; `ЖДЁТ ВЛАДЕЛЬЦА` — ждём ответа, стадия стоит.

Режимы различаются только тем, где ты ждёшь: `co-design` — на каждой развилке внутри стадии, `assisted` — на гейте, `auto` — не ждёшь, но каждое своё решение пишешь `[!auto]` в файл стадии и строкой `auto` в `logs/DECISIONS.md`.

## Остановка в любом режиме

- Всё, что уходит наружу от имени владельца: обещание, число, письмо, просьба к заказчику или руководству, публикация. Ты готовишь текст и рекомендацию, отправляет владелец.
- Пересмотр управляющей идеи, смена центральной механики, вырез или добавление столпа, конфликт линз.
- Вопросы-линзы владельцу (`stages/stages.json` → `owner`): задаёшь и записываешь ответ дословно, сам не отвечаешь.
- Вердикт хранителя `BLOCK` или `ЖДЁТ ВЛАДЕЛЬЦА`.
- Свободный чат для детей — только по слову владельца (`method/layers.md`).

## Застряли

Реплика дискомфорта — «скучно», «не пойму, что делать», «бесит», «выборы фальшивые»: `scripts/pick_lenses.py <папка игры> --stage N --symptom "реплика"` даёт до трёх линз. Подай их с вопросами и спроси, прогоняем ли через них дизайн или зонд: линзу подаёшь в руку, смотрит через неё человек. Итерации буксуют — вопрос 112 «Ворон» (`--owner stall`); автор устал — 113 «Тайная цель» (`--owner fatigue`).

## Готово, когда

- все стадии в `OK` или `SKIP` с причиной, после каждой была сверка хранителя;
- нет необработанных `[!owner]`, ответы из чата записаны в `logs/DECISIONS.md`;
- Библия пересобрана, владелец получил пути: `BIBLE.md`, `07-release/PITCH.md`, зонды, журналы и список открытых вопросов;
- если был веб-зонд — сказано, что это зонд, а не релиз-кандидат.

Хочет билд — `07-release/BUILD-HANDOFF.md` по шаблону `templates/BUILD-HANDOFF.md`: сборка строится с нуля по спецификации.

## Границы

- `BIBLE.md` собирает скрипт и руками не правится; в корне папки игры — только он (`method/game-folder.md`).
- Линзы, шаблоны, роли и правила скилла не правятся в ходе работы над игрой: грабли проекта идут в `logs/errors.json`, а дыра в самом скилле — в его `docs/LESSONS.md` у сопровождающего.
- Текст линз — своими словами по русскому изданию 2019 года (перевод второго издания). Номер и название из русского издания стоят рядом, чтобы читатели перевода нашли линзу в книге.
