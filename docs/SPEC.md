# SPEC — `design-game`: пайплайн гейм-дизайна по линзам Джесси Шелла

> Статус: **черновик на согласование** · Дата: 2026-06-23 · Автор контекста: Александр Пронин
> Это спецификация **самого скилла** (мета-документ). Код/агенты пишутся только после аппрува этой спеки.

---

## 1. Что это и зачем

`design-game` — мульти-стадийный оркестратор, который ведёт от **идеи игры до релиза** через **линзы Джесси Шелла** («The Art of Game Design: A Book of Lenses»). Скилл не «генерит диздок одной кнопкой» — он ведёт диалог по шагам, на каждом шаге применяя релевантный набор линз (фокус-вопросов), и собирает **растущий диздок** + **живой журнал ответов на линзы**.

Архитектурно — близнец `neurowriter/`: глобальный скилл-оркестратор + субагенты-стадии + Markdown-артефакты, статус каждой стадии `OK | BLOCK`.

**Масштаб-агностичен:** работает и для AAA-концепта, и для миниигры на 5 минут. Разница — в глубине применения линз и числе стадий, **но не в наличии управляющей идеи** — она обязательна всегда.

## 2. Философские принципы (откуда растут все решения)

Эти принципы — не украшение, из них выводится каждая механика скилла.

### 2.1. Управляющая идея — стержень всего

Центральный концепт Шелла: **Essential Experience** + **Lens of Unification** (всё ли в игре работает на тему?). У нас управляющая идея:

- формулируется **первой**, в стадии 0, в одно предложение;
- живёт в шапке **каждого** артефакта (`CONTROLLING-IDEA.md`);
- является эталоном, с которым **обязан** сверяться каждый стадийный субагент;
- для миниигры она просто короче — но она есть.

> Любой элемент (механика, баланс, нарратив, интерфейс), который не усиливает управляющую идею, — кандидат на вырезание. Это и есть линза Unification, вшитая в процесс.

### 2.2. Живой журнал линз (а не разовый опрос)

Ответы на вопросы линз **приходят по ходу разработки**, не за один присест. Поэтому ведётся `LENS-LOG.md` — накопительный журнал: `Линза | Вопрос | Ответ | Стадия | Дата | Статус`. Ответ может быть «пока открыт» и закрыться через три стадии. Это честнее, чем заставлять отвечать на всё сразу.

### 2.3. Обратная сверка после каждого этапа (Rule of the Loop)

«Правило петли» Шелла: дизайн никогда не делается за один проход. После закрытия любой стадии запускается **gd-keeper** — он переаудитит **все предыдущие** стадии на:

1. **дрейф от управляющей идеи** (Lens of Unification / Holographic Design);
2. **внутренние противоречия** (механика vs нарратив vs баланс);
3. **красные флаги релевантных линз**.

Результат — `CONSISTENCY.md` (вердикт по каждой стадии: OK / DRIFT + что именно + какая линза + предложенная правка). Серьёзный дрейф → `BLOCK` → оркестратор поднимает к пользователю → петля.

### 2.4. Прототип = одноразовый зонд, а не старт разработки

Позиция Шелла (глава об итерациях) разрешает напряжение «прото vs чистая идея»:

- **«Answer a question»** — у каждого прототипа ровно один рискованный вопрос.
- **«Forget quality» / «Don't get attached»** — качество неважно, важен ответ; готов выбросить.
- **«Build a toy first»** (Lens of the Toy) — сначала проверь, что ядро приятно тискать, ещё до целей.
- **«It doesn't have to be digital»** — бумага/таблица/ASCII держат тебя в пространстве идеи, а не инженерии.

Идейность ломает **не** прототип, а **привязанность** к нему как к «началу продукта». Поэтому каждый зонд декларирует свой вопрос и помечен `disposable`.

### 2.5-bis. Advergame-overlay: правдивость обещаний (serious / advergame)

Для **рекламных и обучающих** игр (advergame / serious game) добавляется сквозной слой ответственности. Триггерится в брифе (тип игры = `advergame / serious`), для `entertainment` не активен.

- В стадии 0 фиксируется **Secret Purpose** (линза Шелла — настоящая внеигровая цель, напр. «правдивый лидген») + **truth-ограничения** → секция в `CONTROLLING-IDEA.md`.
- Линзы **Secret Purpose + Honest Claim + Responsibility** вытягиваются из стадии 7 вперёд: ограничивают **стадию 3** и делают **стадию 7 обязательной** (не skippable даже на `mini`).
- Ключевое правило: **число-наружу = источник или иллюстративная пометка.** Любое число/обещание, которое игра выносит наружу как реальный claim (экономия ₽/%/время), обязано быть правдивым и защитимым — иначе для рекламы это подрывает доверие. Endogenous Value покрывает ценность **внутри** игры; как только ценность становится реальным обещанием наружу — она уходит под Honest Claim / Responsibility. `gd-balance` не выдумывает такие числа молча, `gd-keeper` ловит их как `DRIFT (Responsibility / Honest Claim)`.

### 2.5. Engine-agnostic ядро

Линзы Шелла работают для настолок, аттракционов, видеоигр. Движок входит в скилл **только в трёх точках**: тетрада «Технология», стадия «Прототип», стадия «Релиз». Всё остальное движко-независимо.

**Лестница «самой лёгкой формы» прототипа** (выбирается под вопрос шага):

| Рискованный вопрос про… | Форма зонда | Код? |
|---|---|---|
| баланс / экономику | таблица-симуляция (markdown/CSV) | нет |
| структуру решений / петлю | бумажный / текстовый прото, ASCII-сим | нет |
| **ощущение, тайминг, управление, «сочность»** | **веб: TS + Phaser/Canvas** | да |

Веб берётся как основной кодовый профиль, потому что **только его Claude Code может и собрать, и запустить/увидеть** прямо здесь (через Playwright MCP) — так плейтест-петля реально замыкается в чате. Godot/Unity — будущие профили (запуск ручной).

## 3. Архитектура

### 3.1. Два слоя: portable design layer + per-tool adapters

Скилл задуман **переносимым между тулзами** (Александр отдаёт его людям). Поэтому:

- **Portable design layer** (чистый Markdown, tool-agnostic): библиотека линз, спеки ролей (тела субагентов), стадийный маппинг, шаблоны артефактов, абстрактные **тиры моделей**. Отдаётся папкой.
- **Per-tool adapters**: тонкие документы, как материализовать роли под конкретный тул и какие модели проставить.

К 2026 все три целевых тула сошлись на одном примитиве — **субагент = Markdown + YAML-фронтматтер с полем `model`**:

| Тул | Где субагенты | Поле модели |
|---|---|---|
| **Claude Code** | `.claude/agents/*.md` | `model: opus\|sonnet\|haiku` |
| **Cursor 2.4+** | `.cursor/agents/*.md` (и **читает `.claude/agents/`**) | `model: inherit\|fast\|<id>` |
| **Antigravity 2.0** | `.agents/agents.md` + `.agents/skills.md` + `GEMINI.md` | Gemini 3 Pro/Flash, Claude Sonnet/Opus 4.6, GPT-OSS |

Следствие: Claude-Code-набор почти **drop-in** едет в Cursor (расходится только словарь `model`); под Antigravity — транскрипция в его раскладку.

### 3.2. Тиры моделей (абстракция → конкретика)

В core роль помечается **тиром**, не конкретной моделью. `models.md` резолвит тир в модель под тул.

| Тир | Когда | Claude Code | Cursor | Antigravity |
|---|---|---|---|---|
| **reasoning-heavy** | концепт, баланс, keeper (критический аудит/числа) | `opus` | `claude-opus-4.x` | Gemini 3 Pro / Claude Opus 4.6 |
| **balanced-creative** | механики, опыт, нарратив, плейтест, релиз | `sonnet` | `inherit` / `claude-sonnet-4.x` | Gemini 3 Pro / Claude Sonnet 4.6 |
| **mechanical** | сборка прото-скаффолда, питч-вёрстка, форматирование | `haiku` | `fast` | Gemini 3 Flash / GPT-OSS |

Оркестратор при работе под конкретным тулом проставляет в субагенты значение из этой таблицы. Это и есть «каждый оркестратор говорит, какие модели прописывать».

### 3.3. Где что лежит

```
gamedesign/                          ← дом проекта (по образцу neurowriter/)
  CLAUDE.md                          ← правила проекта
  docs/
    SPEC.md                          ← этот файл
  lenses/
    lenses.md                        ← библиотека ~100 линз (имя RU/EN + фокус-вопросы)
    stage-map.md                     ← стадия → линзы + scale-правила + risk-gate
    schell-prototyping.md            ← дисциплина прототипа (правила зонда, лестница форм)
    models.md                        ← тир → модель по тулу
  templates/
    CONTROLLING-IDEA.md  LENS-LOG.md  GDD.md  CONSISTENCY.md  PITCH.md  PROTOTYPE-PROBE.md
  adapters/
    claude-code.md  cursor.md  antigravity.md
  .claude/agents/
    gd-keeper.md  gd-concept.md  gd-mechanics.md  gd-balance.md
    gd-experience.md  gd-narrative.md  gd-playtest.md  gd-release.md  gd-prototyper.md

.claude/skills/design-game/
  SKILL.md                           ← глобальный оркестратор (entrypoint Claude Code)
```

> Тела субагентов (`gd-*.md`) пишутся **tool-agnostic** — это и есть portable layer; фронтматтер `model:` берётся из `models.md`. Cursor-адаптер = «скопировать в `.cursor/agents/`, заменить словарь model». Antigravity-адаптер = «транскрибировать в `.agents/agents.md`».

### 3.4. Артефакты одной игры (куда — спрашиваем в брифе)

Расположение per-game спрашивается на старте (`games/<slug>/`, route в сайте, отдельная папка — на выбор). Базовый набор:

```
<game-path>/
  CONTROLLING-IDEA.md     ← стержень; шапка всего; создаётся первым
  LENS-LOG.md             ← живой журнал ответов на линзы
  GDD.md                  ← мастер-диздок; растёт раздел за разделом
  CONSISTENCY.md          ← журнал аудитов gd-keeper (аппендится после каждой стадии)
  PITCH.md                ← питч one-pager (стадия 7)
  prototypes/             ← (если режим с прото) зонды: probe-NN-<вопрос>/ + PROTOTYPE-PROBE.md
```

Стадии идут **последовательно** (как neurowriter): один растущий `GDD.md` = один писатель за раз, без гонок.

## 4. Пайплайн стадий

Каждая стадия: **цель → набор линз → артефакт → агент**. После каждой — **gd-keeper** (обратная сверка). Любая может вернуть `BLOCK`.

| # | Стадия | Цель / артефакт | Ключевые линзы | Агент |
|---|---|---|---|---|
| **0** | **Сердце опыта** | Управляющая идея в 1 предложение + желаемый опыт/эмоция + для кого + масштаб → `CONTROLLING-IDEA.md` | Essential Experience, Emotion, Surprise, Fun, Curiosity, Endogenous Value, Problem Solving | оркестратор (интервью) + gd-concept огранивает |
| **1** | **Концепт** | Тетрада (Механика/История/Эстетика/Технология), портрет игрока, тема, крючок → раздел GDD + one-pager | Holographic Design, Unification, Resonance, The Player, Pleasure, Flow, Motivation, Elemental Tetrad | **gd-concept** |
| **2** | **Ядро и механики** | Core loop; пространство/объекты/действия/правила; цели; значимые выборы → раздел GDD (+ прото-зонд) | The Toy, Mechanics (Space/Objects/Actions/Rules), Goals, Meaningful Choices, Triangularity, Skill, Chance, Expected Value | **gd-mechanics** (+ gd-prototyper) |
| **3** | **Баланс** | 12 типов баланса, экономика, кривые сложности → раздел GDD (+ таблица-симуляция) | Fairness, Challenge, Reward, Punishment, Simplicity/Complexity, Elegance, Balance, Economy | **gd-balance** (+ gd-prototyper) |
| **4** | **Опыт и интерфейс** | Кривая интереса, красота/эстетика, интерфейс, фидбэк, «сочность», непрямое управление → раздел GDD | Interest Curve, Inherent Interest, Beauty, Projection, The Interface, Feedback, Juiciness, Channels & Dimensions, Indirect Control | **gd-experience** |
| **5** | **История и мир** (skippable для миниигр) | Нарратив, мир, аватар, персонажи, story-machine → раздел GDD | The Story, The World, The Avatar, Character, Story Machine, The Obstacle, Indirect Control | **gd-narrative** |
| **6** | **Плейтест и итерации** | План тестов, петля итераций, карта рисков → `PLAYTEST` секция (+ реальный играбельный билд, если режим) | The Playtest, The Loop (Rule of the Loop), The Team | **gd-playtest** (+ gd-prototyper) |
| **7** | **Релиз и бизнес** | Питч, комьюнити, монетизация, ответственность, тех-/деплой-план → `PITCH.md` + раздел «Релиз» | The Pitch, The Profit, Transformation, Responsibility, Community, Griefing (для мультиплеера) | **gd-release** |

> Нумерация линз в таблице — по именам (нумерация в изданиях книги плавает). Источник истины по точным формулировкам — `lenses/lenses.md`.

### Scale-адаптация

В `CONTROLLING-IDEA.md` фиксируется `scale: mini | small | medium | large`. Он управляет:

- **набором стадий** (mini может пропустить 5 «История», ужать 3 «Баланс»);
- **глубиной линз** (mini: 3–4 ядровые линзы на стадию; large: полный набор);
- управляющая идея и gd-keeper работают **на любом масштабе**.

## 5. Прото-режим (зонды по Шеллу)

- **Фасонится в брифе:** `docs-only` или `docs + прото-зонды по запросу` (спрашиваем каждый раз, без дефолта).
- **Не автоматом.** На стадиях 2/3/6 (и по запросу на любой) — **risk-gate**: «есть тут рискованное допущение, которое дешевле проверить зондом, чем спорить на бумаге?». Если да — **gd-prototyper**.
- **gd-prototyper** на входе берёт: управляющую идею + ответы линз стадии. Делает:
  1. формулирует **ОДИН вопрос** зонда;
  2. выбирает **самую лёгкую форму** по лестнице (§2.5);
  3. собирает зонд (бумага-спека / таблица / ASCII-сим / веб-билд);
  4. для веба — открывает через Playwright, снимает, что игралка делает;
  5. пишет `PROTOTYPE-PROBE.md`: вопрос → форма → результат → вывод для диздока, помечает `disposable`.
- Вывод зонда возвращается в `LENS-LOG.md` и в соответствующий раздел GDD. Привязываться к коду зонда **запрещено** — это проба, не продукт.

## 6. Контракт субагентов

Все `gd-*` — единый контракт (как `article-*`): читают контекст → пишут артефакт → возвращают оркестратору `OK | BLOCK + причина`. **Обязательно** у каждого: первым делом прочитать `CONTROLLING-IDEA.md` и сверить свою работу с ней.

| Агент | Тир | tools | Роль |
|---|---|---|---|
| **gd-keeper** | reasoning-heavy | Read, Grep, Glob, Write, Edit | Хранитель управляющей идеи + аудит связности всех стадий → `CONSISTENCY.md`. Может `BLOCK`. |
| **gd-concept** | reasoning-heavy | Read, Write, Edit | Огранка управляющей идеи + концепт (тетрада/игрок/тема) + one-pager. |
| **gd-mechanics** | balanced-creative | Read, Write, Edit | Core loop, механики, значимые выборы. |
| **gd-balance** | reasoning-heavy | Read, Write, Edit, Bash | Баланс, экономика, кривые сложности (числа → может звать таблицу-симуляцию). |
| **gd-experience** | balanced-creative | Read, Write, Edit | Кривая интереса, интерфейс, фидбэк, «сочность», непрямое управление. |
| **gd-narrative** | balanced-creative | Read, Write, Edit | История, мир, аватар, персонажи. Skippable для mini. |
| **gd-playtest** | balanced-creative | Read, Write, Edit | План плейтеста, петля итераций, риски. |
| **gd-release** | balanced-creative | Read, Write, Edit | Питч, комьюнити, монетизация, ответственность, тех-/деплой-план. |
| **gd-prototyper** | balanced-creative | Read, Write, Edit, Bash, (Playwright) | Лёгкий одноразовый зонд под один вопрос. |

> Оркестрация — это сам SKILL.md (отдельного агента-координатора нет, как и в `write-article`).

## 7. Поток работы (happy path)

```
Шаг 0  Бриф: режим (docs-only / +прото), масштаб, где артефакты, мед­иум/движок (если важен)
Шаг 1  CONTROLLING-IDEA.md (управляющая идея + опыт + scale) ← интервью, обязательно
Шаг 2  Для каждой стадии 1..7 (с учётом scale):
         a) стадийный агент применяет линзы → дописывает GDD + LENS-LOG
         b) (если прото-режим и risk-gate сработал) gd-prototyper → зонд
         c) gd-keeper → обратная сверка всех стадий → CONSISTENCY.md
         d) BLOCK? → к пользователю, петля. OK? → следующая стадия
Шаг 3  Финал: собранный GDD.md + PITCH.md + (опц.) играбельный билд + список зондов
```

### BLOCK-логика

- **gd-keeper BLOCK** (дрейф от управляющей идеи / противоречие) → показать `CONSISTENCY.md`, пользователь решает: править стадию / пересмотреть управляющую идею / принять осознанно.
- **gd-prototyper «вопрос провалился»** → зонд показал, что допущение неверно → это **успех зонда**; вернуть стадийному агенту на пересборку решения.
- **stage agent BLOCK** (не хватает входных решений) → собрать недостающее у пользователя, перезапустить.

## 11. Разделение «человек / агент» и руль автономии

**Принцип (не обсуждается):** в гейм-дизайне продукт — это **суждение дизайнера**. Авто-прогон творческих ставок автоматизирует ровно то, что нельзя. Поэтому **агент = спарринг-партнёр + писарь + зондировщик + аудитор; человек делает ставки.**

| Делает ЧЕЛОВЕК (ставки) | Делает АГЕНТ (механика/ассист) |
|---|---|
| Управляющая идея, сердце опыта | Прогон фокус-вопросов линз → выкладка ответов и напряжений |
| Центральная метафора / механический крючок, тема | Драфт документации (GDD-разделы, one-pager, питч) |
| Разрешение конфликтов линз, вкус / feel | Математика баланса, симуляции |
| «Достаточно ли хорошо» | Сборка disposable-зондов, прогон через Playwright |
| Truth / этические границы (advergame) | Аудит связности (`gd-keeper`) |
| Приоритеты рисков, вырез/добавление столпа | Форматирование, bookkeeping, ведение логов |

**Руль автономии — 3 режима:**
- **`co-design` (дефолт)** — агент предлагает, человек решает каждую ключевую развилку.
- **`assisted`** — агент драфтит, человек ревьюит/аппрувит на гейтах стадий.
- **`auto`** — агент гонит, человек смотрит на гейтах/финале; но **каждое самостоятельное решение пишется в decision-log** (auto ≠ слепо).

**Правила руля:**
1. Режим выбирается на старте; перед выбором скилл **в чате поясняет, что будет в каждом флоу**.
2. **На каждом гейте** скилл напоминает текущий режим и что произойдёт дальше (выбор владельца — «вариант 2», подробное напоминание).
3. Переключение **двустороннее, в любой точке аппрува**: `co-design ↔ assisted ↔ auto` (напр. «база ясна → `auto` на вёрстку зонда»; и обратно — если на ревью ёкнуло).
4. На тормозе (BLOCK / развилка): агент даёт **рекомендацию + открытый вопрос со свободным вводом** (можно «да» по рекомендации или вписать своё).
5. **Ключевая развилка** (агент обязан тормозить даже в `assisted`): пересмотр управляющей идеи; смена центральной механики; конфликт линз; любое **внешнее обещание** (advergame); вырез/добавление столпа.

## 12. Подбор линз: две оси + foundational + застрял-режим

**Проблема v1:** `stage-map` резал линзы **по scale** фиксированным подсписком → нужные линзы не доходили (доказано: `Honest Claim` и `Curiosity`/`Functional Space` были обрезаны mini-подсписком и не сработали). Это **учебный план, а не toolbox Шелла**.

**Тегирование каждой линзы в `lenses.md`** (мета-блок к линзе):
- `tier`: `foundational` (всегда-кандидат: **Essential Experience, The Toy, Flow, Curiosity** + ядро) | `situational`.
- `categories` (когда релевантна): `advergame`, `multiplayer`, `narrative`, `competitive`, `kids`, `real-money`, `spatial/level`, `economy`, …
- `diagnoses` (симптомы-затыки): «скучно», «нечестно», «не понимаю, что делать», «нет напряжения», «выборы фальшивые», «не цепляет», «теряюсь в пространстве», …
- `stages`: дефолтные стадии.

**Два режима подбора:**
- **Проактивный** (по ходу пайплайна): `обязательное ядро стадии` + `foundational` + **pull по `categories`** из свойств игры — **не по scale.** Свойства/риски игры (теги) агент инферит → **человек подтверждает в брифе**. `Advergame-overlay` (§2.5-bis) — частный случай этого механизма, обобщается.
- **Реактивный — «застрял-режим»** (toolbox Шелла, assisted): агент ловит **реплику дискомфорта** («бесит / не пойму / что-то не так») → мапит на `diagnoses` → подаёт **2–3 линзы-кандидата** с их вопросами → «прогоним дизайн/прото через эту?». Агент **подаёт линзу в руку**, решает человек.

**Анти-перегруз:** дизайнеру показывается только отобранное (ядро + foundational + pull), полная колода — по запросу. Foundational-5 держатся на виду независимо от scale/категории.

## 13. Лог-архитектура: рассуждение (.md) vs данные (JSON)

**Водораздел — не «формат ради формата», а природа записи:**

| Природа | Формат | Артефакты |
|---|---|---|
| **Рассуждение** (аргумент для человека) | `.md` | `GDD.md`, ответы в `LENS-LOG.md`, аудиты `CONSISTENCY.md`, история зонда `PROTOTYPE-PROBE.md` |
| **Данные** (замеры, статусы, для машинных проверок) | **JSON** | `probe.json`, `lens-log.json` (тонкий индекс), `errors.json` |

- **`probe.json`** на каждый зонд (пишет субагент-разработчик прототипа-кода): `{id, вопрос, форма, константы, замеры/траектория, вердикт, disposable, links, ts}`. Сюда уходят данные вроде траектории `14→8→7→13→19→23`.
- **`lens-log.json`** — **тонкий индекс** (без прозы): `{lens, stage, status, link}`. Польза: `gd-keeper` перед финалом машинно ловит «стадия 7 закрыта, а `Fairness` ещё `open`» и не даёт объявить игру готовой. Полные ответы — в `LENS-LOG.md`.
- JSON и `.md` — **не дубль**, а разделение по природе. Прозу (рассуждение) в JSON не пихаем — станет хуже для дизайнера.

## 14. Грабли и обучение между проектами

**Две природы ошибки — не мешать (это решает риск «системная ≠ проектная»):**
- **(A) Ошибка ПРОЕКТА** («гидра слишком быстрая», «число вышло рандомным») → `errors.json` в папке игры, **заводится заново под каждую игру**, на другой проект не уходит.
- **(B) Дыра СИСТЕМЫ** («скилл не спрашивает про правдивость у рекламных игр») → **не лог, а правило**: абстрагируется (без проектной специфики) → чинится в поведении (агент/линза) → строка в maintainer-`LESSONS.md`.

**Промоушен:** `ошибка проекта → ревью «спецификой или дыра системы?» → спецификой: остаётся в errors.json; система: абстрагируй → правь поведение → LESSONS`. **Сырое НИКОГДА не промоутится** в скилл.

**Публикация:** опубликованный скилл везёт **закалённое поведение** (исправления как улучшения) + **runtime-лог граблей ПУСТ** (каждый юзер копит свой `errors.json`). Наши проектные ошибки наружу не текут.

`errors.json` формат: `{id, симптом, корень, фикс, стадия/агент, дата, scope: project|system}`. Грабля #001 (system) = advergame-truth → уже промоучена в поведение (gd-balance/keeper + линза Honest Claim).

## 17. ТЗ-контракт, проверка соответствия и модельная архитектура

**Два слоя ревью (не путать):**
- **Стратегическое — `gd-keeper`:** сходится ли вся игра с управляющей идеей (кросс-стадийно, Unification).
- **Тактическое — проверка «ТЗ→результат»:** выдал ли *этот* субагент то, что в его ТЗ (по одному агенту, критерии приёмки).

**ТЗ-перед-запуском.** Перед каждым субагентом формируется мини-ТЗ (acceptance-spec): цель · ожидаемый артефакт + свойства · какие линзы прогнать · **критерии приёмки** (по чему поймём, что годно). ТЗ — токен-СБЕРЕГАТЕЛЬ: 5 строк дешевле переделки мис-таргетнутого агента.

**Масштабирование ревью по автономии (привязано к §11):**

| Режим | ТЗ пишет | «ТЗ→результат» проверяет | Стоимость |
|---|---|---|---|
| `co-design` | человек (или агент-драфт + аппрув человека) | человек на гейте | дёшево, без доп. агентов |
| `assisted` | оркестратор драфтит → человек аппрувит | оркестратор + человек на гейте | средне |
| `auto` | оркестратор, ТЗ логируется | **opus-верификатор** (отдельный чек), всё в `decision-log` | дорого — цена несмотрящего auto |

**Тип проверки:**
- **Объективное/проверяемое** (билд запустился; линза отвечена; симуляция показывает заявленное) → **дешёвый автоматический чек оркестратором всегда**, в т.ч. в `co-design`.
- **Субъективное/качество** (feel, метафора, вкус) → человек в `co-design`/`assisted`, opus-верификатор в `auto`.

**Модельная архитектура:**
- **Оркестратор = сильная модель** (Claude Code: `opus`; Cursor/Antigravity — топ-тир из `models.md`): пишет ТЗ, диспатчит, верифицирует соответствие, ведёт `decision-log`, держит застрял-маршрутизацию.
- **Субагенты = свой тир** (`models.md`) — работают на более лёгких моделях.
- **opus-верификатор** (reasoning-heavy) поднимается **только в `auto`/high-stakes** — иначе плата за ревью не берётся.

**Экономия токенов (параллельная дока):** субагент получает **тугое ТЗ + указатели на разделы доки**, а не весь контекст; отдельный ревьюер — только `auto`/high-stakes, иначе self-check оркестратора; ТЗ + `decision-log` + `probe.json` — слой shared-state, чтобы не гонять контекст по кругу.

**Структурные решения по субагентам (обновляют §6):**
- **Застрял-режим — логика оркестратора** (не агент): реплика дискомфорта → `diagnoses` из `lens-index.json` → подаёт 2–3 линзы.
- **`gd-prototyper` расщепляется:** `gd-prototyper` (reasoning) — **дизайн зонда** (один вопрос + форма), НЕ кодит; **`gd-builder`** (новый, balanced-creative) — **код зонда** + прогон Playwright + пишет `probe.json` (владелец JSON-лога зонда).
- **`gd-keeper`** дополнительно читает `lens-log.json` (ловит открытые линзы перед финалом) и `errors.json`.
- **Оркестратор — единственный писатель** `lens-log.json` (тонкий индекс) и `decision-log`; стадийные агенты дописывают свой `.md`.
- **Pre-flight:** каждый агент перед стартом читает `errors.json` (проект) — не наступать на свои грабли.
