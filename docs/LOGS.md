# LOGS.md — Правила лог-архитектуры скилла design-game

> Источник истины: §13 SPEC.md («Лог-архитектура»).  
> Этот файл — краткая операционная шпаргалка: кто что пишет, когда читает, что скрывается при публикации.

---

## 1. Водораздел: рассуждение (.md) vs данные (JSON)

Не «формат ради формата» — природа записи определяет формат.

| Природа записи | Формат | Артефакты |
|---|---|---|
| **Рассуждение** — аргумент для человека, история решения | `.md` | `GDD.md`, `LENS-LOG.md` (ответы на линзы), `CONSISTENCY.md` (аудиты gd-keeper), `PROTOTYPE-PROBE.md` (история зонда) |
| **Данные** — замеры, статусы, машинные проверки | **JSON** | `probe.json` (замеры зонда), `lens-log.json` (тонкий индекс линз), `errors.json` (грабли проекта) |

**Правило:** прозу (рассуждение) в JSON не пихаем — станет хуже для дизайнера и тяжелее для агента.

## 2. Кто что пишет

| Лог-файл | Кто пишет | Когда |
|---|---|---|
| `GDD.md` | стадийные агенты (`gd-concept`, `gd-mechanics`, …) | каждая стадия дописывает свой раздел |
| `LENS-LOG.md` | стадийные агенты | новые записи после каждой стадии; статус `open` или `closed` |
| `CONSISTENCY.md` | `gd-keeper` | аппендится после каждой стадии |
| `PROTOTYPE-PROBE.md` | `gd-prototyper` | одна запись на зонд (вопрос → форма → результат → вывод) |
| `probe.json` | **`gd-builder`** | после прогона кодового зонда (замеры, траектории, вердикт) |
| `lens-log.json` | **оркестратор** (SKILL.md) | обновляет индекс при каждом изменении статуса линзы |
| `decision-log` (в `GDD.md` или отдельно) | **оркестратор** | только в режиме `auto` — каждое самостоятельное решение |
| `errors.json` | стадийные агенты / оркестратор | при обнаружении ошибки в ходе работы |

**Ключевое разделение:**
- `lens-log.json` (индекс) — пишет **только оркестратор**; стадийные агенты пишут только в `LENS-LOG.md`.
- `probe.json` (данные зонда) — пишет **только `gd-builder`** (не `gd-prototyper`; prototyper = дизайн зонда, builder = код + замеры).

---

## 3. Pre-flight чтение errors.json

Каждый агент (`gd-*`) **перед стартом работы** читает `errors.json` текущей игры.  
Цель: не наступить на уже зафиксированные грабли этой же игры.

Если файл пуст или отсутствует — продолжать без блокировки.

---

## 4. Как gd-keeper использует lens-log.json

Перед объявлением финала (конец стадии 7 или по явному запросу):
1. Читает `lens-log.json`.
2. Ищет записи со `"status": "open"`.
3. Если открытые линзы есть — формирует список в `CONSISTENCY.md` и возвращает `BLOCK`.
4. Пользователь решает: закрыть линзу / принять осознанно / пропустить с пометкой.

## 5. Что скрывается при публикации (.gitignore)

При передаче скилла другим — опубликованная версия **не содержит** runtime-логов конкретных проектов:

```gitignore
# Артефакты игр — приватны
games/
errors.json
probe.json
prototypes/
*.env
```

Наружу уходит только:
- закалённое поведение агентов (исправления уже вшиты);
- `LESSONS.md` — только абстрагированные уроки (без проектной специфики);
- `lens-log.json` и `LENS-LOG.md` — пустые шаблоны (не заполненные данными конкретной игры).
